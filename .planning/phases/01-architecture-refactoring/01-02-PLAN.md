# Phase 1 Plan 02: Frontend Settings Typing Recovery

## Objective

Stabilize the frontend settings consumption layer after the Phase 1 path consolidation.
This plan does not add features. It closes the gap between the unified `useSiteSettings()`
path and the blog components that still consume settings as `unknown`.

## Why This Exists

Plan 01 unified the runtime path, but `type-check` still shows that many blog components
read properties from `settings.value` without a typed contract. This creates a fragile
"single path, weak schema" state that will slow future frontend work.

## Execution Targets

1. Add a typed frontend settings contract near `useSiteSettings()`
2. Return typed helpers for the blog components that currently read raw `unknown`
3. Update key consumers to use typed config blocks instead of direct `unknown` access
4. Re-run type-check and isolate remaining non-phase errors

## First Consumers To Fix

- `apps/site/components/blog/AnnounceWidget.vue`
- `apps/site/components/blog/BlogNavbar.vue`
- `apps/site/components/blog/CommentWidget.vue`
- `apps/site/components/blog/ProfileWidget.vue`
- `apps/site/components/blog/Sidebar.vue`
- `apps/site/components/blog/WechatWidget.vue`

## Boundaries

- Do not redesign `useTheme()` in this plan unless required for compilation
- Do not migrate unrelated admin pages
- Do not normalize every blog component in one pass if it is unrelated to settings typing

## Success Criteria

- Settings-driven blog components stop reading `unknown` properties directly
- `useSiteSettings()` exposes a clearer typed surface for the homepage/blog shell
- Any remaining `type-check` failures are either outside this scope or clearly identified
