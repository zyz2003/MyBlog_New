# Phase 1 Plan: Recovery / Settings & Theme Chain

## Objective

基于当前代码库的真实状态，Phase 1 不是功能扩展阶段，而是恢复性重构阶段。
这一阶段只处理设置链路与主题链路的收口问题，目标是减少重复入口、统一运行时心智模型，
为后续 Phase 2 和 Phase 3 打下可靠基础。

本阶段只覆盖：

- 前台配置读取统一到 `useSiteSettings()`
- 后台 2-3 个关键设置页迁移到 `useAdminSettings()` 模式
- 主题保存、读取、激活、注入统一以 `/api/themes/*` 为主入口
- `useAdminSettings(category)` 的读取语义开始收口，减少“名义按分类、实际全量抓取”的错位

本阶段明确不覆盖：

- navbar/footer/archive 的补齐或重做
- search/comments 等后续能力
- 所有后台设置页一次性迁完
- 整个 settings API 的彻底重设计

## Current Reality Snapshot

以下事实已经在当前代码中确认，后续执行必须以这些事实为准：

- `apps/site/composables/frontend/useSiteSettings.ts` 已存在，但 `apps/site/pages/index.vue` 和 `apps/site/components/blog/BannerGroup.vue` 仍然直接读取 `/api/settings`
- `apps/site/composables/admin/useAdminSettings.ts` 已存在，`apps/site/pages/admin/sidebar.vue` 已迁移，但 `homepage.vue`、`general.vue`、`display.vue` 等关键页面仍保留各自的 `fetchSettings()/handleSave()` 逻辑
- `apps/site/pages/admin/themes.vue` 已开始走 `/api/themes/${name}/config`
- `apps/site/server/api/themes/[name]/config.post.ts` 已通过 `ThemeManager.saveConfig()` 保存主题配置
- `apps/site/layouts/frontend/default.vue` 已通过 `/api/themes/active.css` 注入当前主题 CSS
- `ThemeManager.saveConfig()` 目前仍会同步写入 `system_settings.themeConfig`，因此这份数据只能视为兼容镜像，不是主题域的一手真相
- `useAdminSettings(category)` 当前读取语义仍然偏弱，本质仍是全量获取 `/api/settings` 后本地拍平，再由页面自行取值

## Invalidated Old Assumptions

以下旧假设已经失效，执行阶段必须主动避开：

1. “已经有 `useSiteSettings()`，所以前台设置链路已经统一”
   实际并非如此，首页和 `BannerGroup.vue` 仍直接请求 `/api/settings`
2. “已经有 `useAdminSettings()`，所以后台设置页已经收口”
   实际只迁了 `sidebar.vue`，关键页并未完成迁移
3. “主题配置属于 generic settings，`system_settings.themeConfig` 是主模型”
   按讨论锁定决策，主题配置属于 theme domain，`/api/themes/*` 才是主入口
4. “本阶段可以顺手把 navbar/footer/search/comments 一起做掉”
   这会越过 Phase 1 的边界，不允许扩 scope
5. “必须一次性重做整个 settings API 才能解决读取语义问题”
   本阶段只做最小必要收口，不升级成全面 API 重构

## Migration Targets Locked For This Plan

本计划固定以下后台迁移目标：

1. `apps/site/pages/admin/homepage.vue`
2. `apps/site/pages/admin/general.vue`
3. `apps/site/pages/admin/display.vue`

说明：

- `homepage.vue` 是已锁定的第一优先级
- `general.vue` 与 `display.vue` 当前重复逻辑较多，适合作为可复用模式样板
- `sidebar.vue` 作为已迁移参考，不作为本计划的新迁移目标

## Task Order

### Task 1. 收口前台读取路径到 `useSiteSettings()`

目标：
把首页及其相关组件对 `/api/settings` 的直接读取收口到单一路径，避免父组件和子组件各自重复抓取配置。

涉及文件：

- `apps/site/pages/index.vue`
- `apps/site/components/blog/BannerGroup.vue`
- `apps/site/composables/frontend/useSiteSettings.ts`
- 如需要补充透传契约，可涉及首页相关 blog 组件

验证方式：

- 静态检查目标文件中不再直接请求 `/api/settings`
- 首页 banner、分类区、today card、sidebar 等配置消费仍然正常
- 类型检查或构建检查未引入新的前台链路错误

范围边界：

- 不重做首页视觉结构
- 不顺带处理 navbar/footer/archive
- 只处理已经确认仍在走旧链路的页面和组件

### Task 2. 迁移关键后台页面到 `useAdminSettings()` 模式

目标：
将 `homepage.vue`、`general.vue`、`display.vue` 迁移到统一的后台设置读写模式，
移除各页面重复的 `fetchSettings()/handleSave()` 结构，但保留各自表单组织方式。

涉及文件：

- `apps/site/pages/admin/homepage.vue`
- `apps/site/pages/admin/general.vue`
- `apps/site/pages/admin/display.vue`
- `apps/site/composables/admin/useAdminSettings.ts`
- `apps/site/pages/admin/sidebar.vue` 仅作为模式参考

验证方式：

- 三个目标页不再保留大段手写 `api.get('/api/settings')` / `api.put('/api/settings')` 逻辑
- 每个页面都能完成“加载 -> 修改 -> 保存 -> 本地状态更新”的闭环
- 已迁移的 `sidebar.vue` 不被破坏

范围边界：

- 不扩展到 comments、features、posts、analytics、seo 等其他后台页面
- 不顺带新增大量字段
- 不把主题页面混入 generic settings 的迁移中

### Task 3. 收口 `useAdminSettings(category)` 的读取语义

目标：
让 `useAdminSettings(category)` 的读取结果更贴近它所管理的 category，
减少页面自己猜测和拆解全量 settings 的负担。

涉及文件：

- `apps/site/composables/admin/useAdminSettings.ts`
- `apps/site/server/api/settings/index.get.ts`
- 如需最小后端支持，可涉及 `apps/site/server/services/settings.service.ts`
- 受影响页面：`homepage.vue`、`general.vue`、`display.vue`、`sidebar.vue`

验证方式：

- `useAdminSettings('homepage')` 的返回结构与首页设置实际需要更贴近
- 已迁移页面在新的读取语义下仍能加载和保存
- 不引入超出本阶段范围的大规模 settings API 改造

范围边界：

- 允许最小增量优化，不允许全面重写 settings 数据模型
- 不要求一次性统一所有后台页面
- 不改变主题域的主入口归属

### Task 4. 验证并固定 Theme Domain 主链路

目标：
把主题域的主链路明确为：

`admin theme page -> /api/themes/* -> ThemeManager.saveConfig()/activate() -> /api/themes/active.css -> frontend layout`

同时明确 `system_settings.themeConfig` 只是兼容镜像，而不是未来继续扩展的主入口。

涉及文件：

- `apps/site/pages/admin/themes.vue`
- `apps/site/server/api/themes/[name]/config.post.ts`
- `apps/site/server/api/themes/[name]/activate.post.ts`
- `apps/site/server/api/themes/active.css.get.ts`
- `apps/site/server/core/theme/manager.ts`
- `apps/site/layouts/frontend/default.vue`

验证方式：

- 主题保存后，数据通过 `/api/themes/[name]/config` 进入 `ThemeManager.saveConfig()`
- 激活主题后，前台继续通过 `/api/themes/active.css` 获得最新变量
- 不再把 `/api/settings` 视为主题主入口

范围边界：

- 只验证并固定主链路，不重做 Theme Customizer UI
- 兼容镜像可以保留，但不能重新升级为主模型
- 不扩展到更大的主题开发系统

## Execution Notes

- 推荐严格按 `Task 1 -> Task 2 -> Task 3 -> Task 4` 顺序执行
- 如果 Task 3 发现确实需要新增“按 category 读取”的最小后端契约，应采取增量收口方式，而不是重构整个 settings API
- 如果 Task 4 发现前台仍真实依赖 `themeConfig` 镜像，应记录依赖点并保留兼容，但不能倒退回 generic settings 心智模型

## Success Criteria

- 首页及其已确认旧路径的前台组件不再直接请求 `/api/settings`
- `homepage.vue`、`general.vue`、`display.vue` 三个关键后台页面完成迁移
- `useAdminSettings(category)` 的读取语义较当前更接近 category 本身
- 主题保存、激活、CSS 注入链路以 `/api/themes/*` 为唯一主心智入口
- 执行过程中不越界进入 Phase 2 / Phase 3 的工作范围
