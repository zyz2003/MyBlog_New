    ```typescript
    static async upsert(
      key: string,
      value: unknown,
      category?: string,
      description?: string,
      tx?: typeof db,
    ) {
      // Validate value against Zod schema (per DATA-02, D-18)
      const validatedValue = validateSettingValue(key, value)

      const dbOrTx = tx || db
      const now = new Date()

      const [record] = await dbOrTx
        .insert(systemSettings)
        .values({
          key,
          value: validatedValue as any,
          category,
          description,
          updatedAt: now,
        })
        .onConflictDoUpdate({
          target: systemSettings.key,
          set: {
            value: validatedValue as any,
            updatedAt: now,
            ...(category !== undefined ? { category } : {}),
            ...(description !== undefined ? { description } : {}),
          },
        })
        .returning()

      return record
    }
    ```

    Key changes from current code:
    - Add `validatedValue` via `validateSettingValue(key, value)` call BEFORE any DB operation
    - Use `validatedValue` in both `.values()` and `.onConflictDoUpdate().set()` instead of raw `value`
    - Use `dbOrTx` instead of `db` for transaction support
    - Validation error propagates naturally (no try-catch needed — caller handles it)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API request body → SettingsService.upsert() | Untrusted JSON values cross from HTTP body into database writes |
| API request body → SettingsService.batchUpdate() | Untrusted array of key-value pairs crosses from HTTP body into database writes |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Tampering | SettingsService.upsert() | mitigate | Zod validation via validateSettingValue() rejects malformed values before DB write — setting keys with known schemas (socialLinks, footer, darkmode, etc.) are validated for correct structure |
| T-01-02 | Tampering | SettingsService.batchUpdate() | mitigate | db.transaction() wrapper ensures atomicity — if any item in the batch fails validation, the entire batch rolls back with no partial writes |
| T-01-03 | Information Disclosure | validateSettingValue() error messages | mitigate | Error messages include key name and validation issue path but do NOT expose database schema internals or SQL details |
| T-01-04 | Denial of Service | batchUpdate() loop | accept | No batch size limit imposed here — the API layer (index.put.ts) already validates body shape. Large batches are a valid admin operation. Rate limiting is deferred to v2.1 (INFR-03) |
</threat_model>
